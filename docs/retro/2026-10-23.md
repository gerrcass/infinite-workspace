# Retrospective: Infinite Workspace v1

**Date:** 2026-10-23
**Scope:** the v1 build, from grilling through merge/deploy.

## What worked

- **Grilling before code.** Pinning the browser-support policy, renderer seam, and find limitation before implementation prevented a late architectural rewrite.
- **Hands-on API probe.** A throwaway Chrome 157 page validated destination-rect drawing, DPR geometry, contenteditable hit-testing, offscreen snapshots, and find highlights before the app existed. That turned guesses into constants.
- **Two-renderer contract.** Keeping all HTML-in-Canvas contact inside one renderer made the fallback and the runtime failover straightforward.
- **Measured, not assumed, performance.** Drawing all 216 cards measured ~1–2 ms/frame, so culling was deliberately not built. This kept find and accessibility geometry for every card.
- **Targeted updates.** Cards are created once; camera moves never re-create DOM or blur fields.

## Findings, in severity order

1. **A stale preview server produced a false test failure.** The failing find-reveal test passed alone but failed in the suite because a long-running `vite preview` served an older bundle. The test itself was fine.
   - **Applied:** added `pretest:e2e` so `npm run test:e2e` always rebuilds; documented the reason in AGENTS.md.
2. **A real editing bug hid behind that flake.** Selecting all text in a focused card moved the camera because the reveal handler could not tell editing from find. The initial fix also treated the first 400 ms after page load as user input because `lastUserInputAt` started at `0`.
   - **Applied:** explicit `editingFocus` state plus a user-input timestamp initialized to negative infinity; regression tests in both renderers.
3. **Native find cannot drive the camera.** Chrome's find bar does not expose its active match as a DOM selection. The original spec overclaimed auto-reveal.
   - **Applied:** spec, help, and README now state the limitation; selection-based reveal is tested and demonstrated separately. No custom find field was added.
4. **Accessibility names were flattened.** `aria-label="Card title"` made all 216 headings announce the same thing, and later `aria-placeholder` did the same.
   - **Applied:** titles mirror their own text into `aria-label`; the AX test asserts real heading names and rejects "Card title".
5. **Delete was over-guarded.** Any focused control blocked Delete, although only text fields should.
   - **Applied:** Delete checks `isEditableTarget`, not all interactive targets; test deletes with a checkbox focused.
6. **Mobile undo/redo were hidden to make the top bar fit.** That made touch deletion irreversible.
   - **Applied:** brand copy collapses below 500 px; undo/redo/help stay visible and are covered by the narrow-viewport test.
7. **Style duplication accumulated.** Three element factories, repeated input-type lists, and duplicated max-card constants. These were judgement calls, not defects.
   - **Applied:** removed unused exports, shared `MAX_SAVED_CARDS`, `EDIT_ASSIST_BELOW_ZOOM`, `worldToScreen`, and `cameraEquals`; kept the tiny element factories because extracting them would add indirection without reducing real duplication.

## Environment improvements applied

- **Automated check:** `pretest:e2e` rebuilds before browser tests.
- **Coding standards:** contract assertions on `content="drawable"`/`drawable` are explicitly allowed in tests; production code outside the canvas renderer still may not name them.
- **Navigation:** AGENTS.md now names the e2e build behavior and the native-find limitation, so the next agent does not rediscover them.
- **Verification access:** `docs/verification.md` records the exact commands, Chrome versions, native-find manual steps, and expected numbers.
- **Tool economy:** the headed-Chrome + Xlib native-find check was expensive. The result is captured in `assets/native-find.png` and the manual steps, so it does not need repeating unless the find behavior changes.

## Follow-ups (not in v1)

- High-zoom re-rasterization: destination-rect drawing upscales snapshots, so text softens above ~2×. A quantized CSS layout scale per card would fix it at the cost of reflow.
- Native find reveal: only solvable by giving the board a native scroll surface or by a future browser API that exposes the active match. Revisit when Chrome ships one.
- A virtualized DOM for boards well above the measured 216–500 range.
